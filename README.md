# DGJ CRM backend — مرحلة تجربة الحسابات والبيانات المشتركة

هذا مشروع خلفي مستقل، جاهز للإعداد على Railway مع قاعدة PostgreSQL الموجودة
عندك. يعمل بـ Node.js 24 وExpress وBetter Auth. حسابات المستخدمين وكلمات المرور
المشفرة بالتجزئة والجلسات والسجلات تُحفظ في PostgreSQL، وليس في GitHub.

**الموقع الحالي على GitHub Pages لم يُربط بهذا المشروع بعد.** هذا الملف يشغّل
API وصفحة اختبار للحسابات والكونتاكت، ثم نربط واجهة الـCRM الحالية بعد معرفة
رابط الخدمة. البيانات الموجودة في متصفح الموقع القديم لا تُنقل تلقائيًا.

## الموجود الآن

- تسجيل دخول بالبريد وكلمة المرور؛ لا يوجد تسجيل مفتوح للزوار.
- أول حساب مديرة يُنشأ مرة واحدة من متغيرات Railway.
- المديرة تضيف حسابات العضوات والمديرات، وتعطّل وتفعّل الوصول. التعطيل يلغي الجلسات.
- تغيير كلمة المرور من الحساب الحالي. لا يوجد إرسال بريد أو «نسيت كلمة المرور» في هذه المرحلة.
- صفحة تجربة بالعربية: إضافة وتعديل وبحث وترقيم صفحات للكونتاكت؛ محذوفات واستعادة وحذف نهائي وتصدير للمديرة.
- API لحفظ Contacts / Opportunities / Meetings / Reports / Complaints / Tasks.
- الصلاحيات تُفحص في السيرفر: السجلات المشتركة متاحة للفريق، والخاص للمديرة المالكة.
- الروابط إلى كونتاكت/فرصة/اجتماع خاص تجعل السجل المرتبط غير متاح لغير المسموح لهم، عبر جميع الروابط.
- الحذف والتصدير والمُحذوفات للمديرة فقط. يظل نسخ البيانات المقروءة ممكنًا.
- رقم نسخة يمنع الكتابة فوق تعديل زميلة؛ مفتاح طلب يمنع تكرار الإضافة عند إعادة المحاولة.
- سجل أحداث بالهوية والتوقيت من السيرفر، وإحصائيات مبنية على البيانات المسموح بها فقط.

## 1. رفع المشروع إلى GitHub

1. فكّي ضغط `DGJ-CRM-backend.zip`.
2. في GitHub أنشئي **مستودعًا جديدًا Private** باسم `dgj-crm-backend`.
3. اختاري **Add file → Upload files**.
4. ادخلي مجلد `DGJ-CRM-backend` وارفعِي **المحتويات** إلى جذر المستودع:
   `package.json`, `package-lock.json`, `Dockerfile`, `railway.json`,
   `src`, `migrations`, `public` وباقي الملفات. ثم **Commit changes**.
5. يجب أن يظهر `package.json` مباشرة عند فتح المستودع. لو ظهر مجلد خارجي
   واحد فقط، ادخلي محتوياته وارفعِيها للجذر، أو حددي ذلك المجلد في Root Directory على Railway.

لا ترفعي ملف ZIP وحده. لا ترفعي `node_modules` أو ملف `.env` حقيقي.
`.env.example` مجرد نموذج بلا أسرار. مستودع واجهة `dgj-crm` يبقى منفصلًا.
لا تحتاجين VS Code أو تثبيت Node لرفع وتشغيل هذا المشروع على Railway.

## 2. إضافة الخدمة إلى مشروع Railway الحالي

1. افتحي **نفس المشروع** الذي فيه `Postgres — Online`.
2. اختاري **+ Add → GitHub Repo**، ثم `dgj-crm-backend`.
   قد يطلب Railway ربط حساب GitHub ومنحه الوصول لهذا المستودع الخاص فقط.
3. افتحي خدمة الباك إند الجديدة؛ لا تضيفي هذه المتغيرات إلى خدمة Postgres.
4. من **Settings → Networking → Public Networking → Generate Domain**
   أنشئي رابطًا للخدمة. إن طلب منفذًا اكتبي `3000`.
5. انسخي الرابط الكامل بـ `https://`. سنستخدمه في `BETTER_AUTH_URL`.

لو أول تشغيل فشل قبل إضافة المتغيرات فهذا متوقع؛ أضيفيها ثم Deploy.
Railway يقرأ Dockerfile وrailway.json. أمر التشغيل موجود: `npm start`؛
فحص الصحة `/health`. لا يحتاج الباك إند Volume مستقلًا؛ البيانات في Postgres.

## 3. المتغيرات — Variables في خدمة الباك إند

| الاسم | القيمة |
| --- | --- |
| `DATABASE_URL` | `${{Postgres.DATABASE_URL}}` |
| `BETTER_AUTH_URL` | رابط خدمة الباك إند، مثل `https://your-service.up.railway.app` بدون مسار أو `/` أخيرة |
| `BETTER_AUTH_SECRET` | مفتاح عشوائي جديد؛ استخدمي أداة التوليد أدناه |
| `APP_ORIGINS` | `https://leenaaloufi.github.io` |
| `NODE_ENV` | `production` |
| `PORT` | `3000` |
| `TRUST_PROXY_HOPS` | `1` لخدمة Railway خلف الـproxy؛ غيّريه إذا تغيرت الاستضافة |
| `DATABASE_SSL` | `false` لاتصال Railway الداخلي في هذه التجربة |
| `BOOTSTRAP_ADMIN_EMAIL` | بريد حسابك للتجربة |
| `BOOTSTRAP_ADMIN_NAME` | `Leena Aloufi` |
| `BOOTSTRAP_ADMIN_PASSWORD` | كلمة مرور فريدة تختارينها، من 12 إلى 128 حرفًا |

**اسم `Postgres` في المرجع يجب أن يطابق اسم خدمة قاعدة البيانات بالضبط.**
يمكن اختيار Add Reference من المتغيرات بدل كتابة الرابط الداخلي يدويًا.
لا تنسخي عنوان قاعدة البيانات أو كلمة المرور إلى HTML أو JavaScript الواجهة.
`APP_ORIGINS` هو أصل GitHub Pages فقط، بدون `/dgj-crm/`.

لتوليد المفتاح: بعد فك الضغط افتحي محليًا
`setup-tools/generate-secret.html` في المتصفح، اضغطي «إنشاء مفتاح»، ثم انسخيه
إلى متغير `BETTER_AUTH_SECRET` على Railway. الصفحة تعمل محليًا ولا ترسل المفتاح.
لا تشاركي صورة للمتغيرات وهي ظاهرة. يمكن إخفاؤها/Seal على Railway بعد ضبطها.

لـPostgreSQL آخر يتطلب TLS: استخدمي `DATABASE_SSL=true`؛ يتم التحقق من
الشهادة، ويمكن إضافة شهادة الجهة في `DATABASE_CA`. لا يُعطّل التحقق من الشهادات.

## 4. تشغيل وتجربة

1. احفظي المتغيرات ثم طبّقي **Deploy / Redeploy**.
2. انتظري نجاح الخدمة. عند أول تشغيل تنشأ الجداول وحساب المديرة تلقائيًا.
3. افتحي الرابط مع `/health`: يجب أن يظهر `{"status":"ok"}`.
4. افتحي الرابط الأساسي، وسجّلي ببريد وكلمة مرور المديرة التي اخترتها.
5. أضيفي حساب عضوة من «حسابات الفريق»، وكونتاكت مشترك وآخر خاص، ببيانات وهمية.
6. افتحي نافذة Incognito وسجّلي بالعضوة. يظهر المشترك، وتختفي الخاص والحذف والتصدير.
7. جرّبي تعديل المشترك ثم تحديثه في حساب المديرة؛ يجب أن يظهر التعديل.
8. جرّبي الحذف والاستعادة من حساب المديرة؛ العضوة لا ترى السجل المحذوف.
9. بعد أول دخول ناجح احذفي **متغير `BOOTSTRAP_ADMIN_PASSWORD`** من Railway ثم
   Redeploy. الحساب يبقى محفوظًا. لا تحذفي `BETTER_AUTH_SECRET` أو تغيّريه كل تشغيل.

كلمات المرور ليست معروفة لنا أو محفوظة في هذا الكود. غيّري كلمة المرور الأولية
من داخل الحساب. لا توجد خدمة بريد مضافة: استعادة كلمة مرور منسية تحتاج خطوة
تجهيز مستقلة لاحقًا، ولا تتوقعين أن تعديل متغير Bootstrap يعيد تعيين الحساب.

الصفحة تحتفظ بالجلسة في ذاكرة التبويب فقط؛ تحديث الصفحة أو إغلاقها يتطلب دخولًا
جديدًا. صلاحية الجلسة 8 ساعات. هذا يتجنب حفظ رموز الدخول أو الكونتاكت في localStorage.

## 5. ما الذي يبقى لواجهة GitHub Pages؟

بعد نجاح التجربة نحتاج **رابط الباك إند العام فقط** لتعديل واجهتك الحالية:

1. نضيف تسجيل الدخول ونقرأ `/api/me` لتحديد الحساب الحقيقي.
2. نزيل تبديل حسابات الديمو والاعتماد على بيانات المتصفح/seed للبيانات المشتركة.
3. نربط نماذج الحفظ بـAPI وننتظر تأكيد السيرفر قبل إظهار نجاح الحفظ.
4. نحفظ رقم النسخة ونرسل If-Match؛ عند تعارض التعديل نطلب إعادة تحميل السجل.
5. نربط الجداول والبحث والرسومات والمحذوفات ببيانات السيرفر المصرّح بها.
6. نحافظ على التصميم الحالي، ونربط تدريجيًا الوظائف الإضافية.

لا يمكن تغيير `persist()` إلى Promise وحدها: الدوال الحالية تستخدم معاملات
متزامنة. نحتاج تحويل مسارات الحفظ والعمليات التي تضيف تقريرًا واجتماعًا ومهام
معًا إلى معاملات API مناسبة قبل اعتبارها مربوطة بالكامل.
الملاحظات والمرفقات وتاريخ الوظائف ودمج التكرارات والإيميلات واستيراد/استعادة
النسخ القديمة ليست endpoints مكتملة في هذه الحزمة. سجلات الأنواع الستة لها
CRUD أساسي؛ سير العمل الكامل في الواجهة لا يُنقل تلقائيًا.

وجود GitHub Pages يبقي ملفات الواجهة عامة؛ حماية البيانات تأتي من API.
هذه الحزمة لا تجعل نسخة الواجهة الحالية محمية أو تحوّل بيانات المتصفح القديمة
إلى بيانات مشتركة بمجرد نشر الخدمة.

## الحدود والانتقال لاحقًا

هذه تجربة مستقلة ببيانات وهمية حتى الموافقة على بيئة الشركة. لا اتصال بـLists
أو Microsoft أو بريد أو MFA في هذه المرحلة. لا توجد شركة خارجية لتسجيل الدخول:
Better Auth مكتبة داخل الكود، لكن Railway هو مزود الاستضافة وPostgreSQL المستضافة.
يمكن نقل نفس محرك PostgreSQL إلى Azure لاحقًا؛ إضافة دخول Microsoft تحتاج إعدادًا
من الشركة، والانتقال إلى Lists يحتاج محولًا ونقل بيانات منفصلًا.

سقف النموذج 10,000 سجل؛ نحتاج تحويل قراءة الرسم إلى استعلامات صلاحيات مناسبة
لأحجام أكبر قبل تجاوز ذلك. عرض الأحداث يغطي آخر 1,000 حدث مخزن، ولا يحذف البقية.
حذف سجل نهائي مرتبط بسجلات أخرى يُرفض إلى أن تُفصل الروابط أو تُحذف السجلات التابعة.
تصدير النوع ملف JSON، وليس نسخة احتياطية كاملة لحسابات المستخدمين والجداول.
النسخ الاحتياطي التلقائي واستعادة قاعدة البيانات يجب ضبطهما منفصلًا.
ظهور Trial على Railway لا يعني استضافة مجانية دائمة؛ راقبي الرصيد والاستخدام.

## تشغيل محلي للمطور

تحتاجين Node.js 24 وPostgreSQL، وملف `.env` حقيقي محليًا فقط:

```bash
npm ci
npm start
```

للاختبارات المحلية، يستخدم `npm test` نسخة PostgreSQL WASM مع pg عبر TCP؛
لا يتصل بـRailway أو بيانات الشركة:

```bash
npm test
npm audit --omit=dev
```

راجعي `API.md` و`VALIDATION.md` للمطور الذي يكمل الربط.
